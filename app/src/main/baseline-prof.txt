# PhotoTidy 应用自身的 baseline profile。
#
# 背景：release 构建本来就会合并依赖库（Compose / AndroidX / Lifecycle / Coil）随 AAR
# 带来的 profile，但 `com/phototidy` 的覆盖一直是 0 —— 也就是说 Compose 自己的关键路径
# 是 AOT 的，应用自己的代码（Application/Activity 入口、依赖容器、设置同步读取、
# 主题构建、首次扫描、首帧）却仍然要冷启动时现 JIT。低端机上「第一次打开什么都慢一下」
# 主要就是这一段。
#
# 这份文件的来源与局限：
#  · 类名不是手写猜的 —— 是从 `app/build/tmp/kotlin-classes/<variant>/com/phototidy`
#    里实际编译出来的 .class 文件枚举出来的（lambda 类折叠到其顶层类的 `**` 通配里），
#    所以每一行都对应真实存在的类。
#  · 但它是**粗粒度**的（类级通配 + 全方法），不是 Macrobenchmark 在真机上跑出来的
#    带调用序/热度的 profile。精度不如生成版，收益也不如生成版稳。
#  · 后续接入 `androidx.baselineprofile` + 一个 macrobenchmark 模块、在真机上跑一次
#    `StartupBaselineProfile` 之后，这份手写文件应当被生成的版本取代并删除。
#
# AGP 会自动读取 src/main/baseline-prof.txt，并在 release 构建时与依赖库的 profile 合并。
